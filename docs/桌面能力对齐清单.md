## P1

### P1-1 数据库写放大（sql.js 全量快照） —— 状态：已完成（三阶段全部落地，待真机验收）

- **证据**：`src/desktop/database/index.js:264-278` 每条写命令都 `db.export()` 整库序列化 + 整文件落盘；原版为 better-sqlite3 增量写
- **现状**：当前库 5.8 MB，等于每改一篇笔记写 5.8 MB；库变大后内存与写放大会同步放大
- **选型**（2026-11-21 拍板）：改用 **rusqlite**
  - rusqlite 0.43.0，crates.io 累计 1.60 亿次下载、近 90 天 6500 万次，MIT，`bundled` 特性直接编译 SQLite 源码
  - 它是 Rust 生态里与 better-sqlite3 形态最接近的一个：同步 API、任意 SQL 字符串、单连接、`BEGIN/COMMIT` 由调用方控制
  - 对比 sqlx（累计 1.92 亿次但为异步多库工具箱：Postgres/MySQL/SQLite 通用 + 编译期宏查询），形态不同，改造成本更高、还需引入 async 运行时桥接，故不选
- **阶段一（已完成）**：Rust 侧 `src-tauri/src/db.rs`
  - `Database` 持 `Mutex<Option<Connection>>`，延迟打开（打开失败变成命令错误，不在启动阶段 panic），库文件仍是 `data_dir/memocast.db`，与 sql.js 写的标准 SQLite 文件互通，无需迁移
  - `db_query(sql, params)` → 对象数组；`db_run(sql, params)` → `{ changes, lastInsertRowid }`；事务靠同一个连接上的 `BEGIN/COMMIT` 跨命令保持
  - 参数绑定只放行 null / 布尔 / 数字 / 字符串（布尔按 1/0 落库，与 sql.js 一致）；BLOB 列不存在，兜底用无损十六进制
  - 前端 `src/desktop/database/engine.js`：`createTauriEngine` / `createSqlJsEngine` 两种前端，接口统一成异步 `query/run`，浏览器预览继续用 sql.js + IndexedDB（`pnpm dev:frontend` 不受影响）
  - 验证：`cargo test` 26 passed（新增 7 条：类型往返、changes/rowid、跨命令事务、布尔绑定、坏 SQL、无参查询、真实文件打开）；`jest` 8 suites 40 tests；`eslint` 0
- **阶段二（已完成，`92c6ffd6`）**：调用方异步化
  - 静态盘点得出真实调用面：**262 处**（`db.run` 139、`execOne` 63、`execToObjects` 40、`db.exec` 10、`getLastInsertRowid` 6、`execRun` 2、`db.prepare` 1、`db.export` 1）
  - 先保持 sql.js 引擎、两套引擎共用同一个库实例（零分叉），逐批迁移完再切引擎；`index.js` 底层助手 `execRaw` / `execToObjects` / `execOne` / `execRun` / `runSql` 全部 async，`getLastInsertRowid` 改读引擎缓存的 `lastRowid`，`initSchema` 改 async，保留 `db = { run, exec, query }` 兼容门面给子服务
  - 落盘策略回到「命令边界统一 flush」：`runSql` 只置 `dirty`，`invokeDatabase` 在 handler 结束后统一 `engine.flush()` —— 与原版「写盘失败 → 命令 reject → 下条命令重试」语义一致。曾试过在 `engine.run` 内落盘，`initSchema` 40+ 条写语句会各导出整库一次（jest 抓到 `writeSnapshot` 45 次）
  - **切引擎**：`DB_ENGINE = isTauri() ? 'tauri' : 'sqljs'`（留 `globalThis.__COOLMA_DB_ENGINE__` 排障开关可强制回退 sql.js）；Tauri 下不再 `loadSnapshot` / `db.export()`，直接读写 `memocast.db`
  - 服务侧同步改异步：`rune-template-service` / `note-template-service` / `deleteEffectBuiltinMigration` 的 `ensureSchema / listAll / saveOne / saveMany / remove` 均为 async
- **阶段三（随阶段二达成）**：Tauri 路径的整库快照读写只在 `DB_ENGINE === 'sqljs'` 分支存在，`database_read` / `database_write` 仅剩浏览器预览与备份用途
- **验证（阶段二）**：jest **12 suites / 72 tests** 全绿（新增 `database-crud.test.js` 6 条 CRUD/标签/设置/模板/分类回归 + `database-tauri-engine.test.js` 3 条，后者用假的 `@tauri-apps/api/core` 把 `db_query` / `db_run` 接到 sql.js 内存库，复刻 `db.rs` 的返回契约，验证「前端异步助手 + Rust 命令契约」闭环、且 Tauri 分支不再碰快照）；`eslint database/index.js` 88（原基线 94）、service 三文件与 HEAD 持平；静态审计确认传给 `runSql` / `execRaw` 的 SQL 全部是单语句（rusqlite `prepare` 不吃多语句）

### P1-2 safeStorage 遗留密文迁移 —— 状态：已完成

- **证据**：原版 `electron-main.js:67-90` 有 CryptoJS 旧版解密分支；Tauri `credential.js` 原先只认 `keyring:` 引用，其余一律返回空串
- **排查补充（比原判断更严重）**：本机真实老库 `%APPDATA%\coolma\memocast.db` 里那行 `api_key_encrypted` 版本号是 **2**，但内容不是引用，而是 Electron safeStorage 的 `v10` 密文 —— 即"AES-256-GCM，密钥由 DPAPI 包裹后存在 `Local State` 的 `os_crypt.encrypted_key`"。所以迁过来的老库 **v1 和 v2 都读不出来**，不只是 v1
- **方案**：两种历史格式都就地解出，解出来即用；下次保存配置时自然升级成 keyring 引用
  - v1：`crypto-js` 按原版机器派生密钥（`包名|版本|userData|platform|arch|hostname` 做 SHA256）；seed 各段都可能变，故由 Rust 出候选密钥列表逐个试解，命中要求明文是可打印 ASCII 且 ≥8 字符
  - v2：Rust `dpapi_unprotect` 做 DPAPI 解封（`CryptUnprotectData`）拿 32 字节 AES 密钥，前端用 WebCrypto `AES-GCM` 解 `v10`/`v11` 密文
- **落地**：`credential.rs` 新增 `legacy_data_dir` / `legacy_key_secrets` / `dpapi_unprotect`；`Cargo.toml` 加 windows 专用的 `windows-sys`（DPAPI 绑定）；`credential.js` 重写读取路径并加会话内明文缓存
- **验证**：Rust `cargo test --ignored` 用真实 `Local State` 解封出 32 字节密钥（`dpapi_unwraps_electron_safe_storage_key` ok）；真实密文经 DPAPI + WebCrypto 解出 35 字符、以 `sk-` 开头的可打印明文；Jest 新增 7 条（v1 往返、错密钥跳过、全错返空、明文形态、v10/v11 切分、DPAPI 前缀剥离）
- **已知边界**：用户若已卸载 Electron 版、`Local State` 随目录被删，DPAPI 密钥随之丢失，只能重填；v1 的 seed 含历史版本号，跨版本的老密文可能已无法解开（原版同样如此）

### P2-3 外部文件拖拽失效 —— 状态：已完成（复扫发现）

- **问题**：`tauri.conf.json` 没写 `dragDropEnabled`，Tauri 默认 `true`。Windows 上开启它意味着 WebView2 的 OS 文件拖放被 Tauri 接管，HTML5 `drop` 事件收不到
- **影响面**：Muya 编辑器靠 `libs-muya-vue2/lib/contentState/dragDropCtrl.js` 的 `dataTransfer.files` 处理"从资源管理器拖图片进来就插图"，Electron 版可用；Tauri 版此前拖进去毫无反应。`rankingTierDialog.vue` 的上传区同理
- **改法**：窗口配置补 `"dragDropEnabled": false`。确认全仓没有用 Tauri 的 `onDragDropEvent`（无引用），关掉不影响任何现有行为
- **后续修正（见 P2-8）**：只加这一行**并不能**让拖拽生效。实测 wry 0.57.3 `webview2/mod.rs:163-170` 只在"设置了 drag-drop handler"时才调 `SetAllowExternalDrop(false)`，所以我们这行确实是 HTML5 `drop` 能收到的前提；但 Muya 自己的 handler 依赖 Electron 的 `File.path`，在 WebView2 里拿不到路径，仍然静默失败。真正的修复是 P2-8
- **验收**：`dragDropEnabled: false` 后 HTML5 `drop` 能收到（P2-8 的接管逻辑据此工作）；拖拽插图最终由 P2-8 交付

### P2-4 标点键快捷键永不命中 —— 状态：已完成（复扫发现）

- **问题**：`shortcutTable.js` 用 `event.key` 比对，但 `KeyboardEvent.key` 会随 Shift 变形：`Ctrl+Shift+,` 实际报 `key='<'`、`Ctrl+Shift+.` 报 `key='>'`，与表里的 `,` / `.` 永不相等
- **影响面**：`view.switch-view`（Ctrl+Shift+,）与 `view.source-mode`（Ctrl+Shift+.）在 Tauri 版完全按不出来 —— 后者正是源码模式开关。原测试用 `key: ','` 造事件，所以测试绿了、真机是死的
- **改法**：`parseAccelerator` 为标点键附 `code`（`Comma`/`Period`/`Equal`/`Minus`/`Backquote`/`Slash` 等），`matches` 优先按 `event.code`（物理键位，不受 Shift 影响）比对；无 `code` 的合成事件仍退回 key 比对
- **验收**：Jest 新增真机形态用例（`key:'<' + code:'Comma'` 命中 switchView、`key:'>' + code:'Period'` 命中 sourceMode），且不带 Shift 的组合不被误放行

### P2-7 正文图片地址跨端不互通 —— 状态：已完成（复扫发现）

- **问题**：原版把笔记正文里的图片写成 `coolma://coolma.app/<kb>/<doc>/<name>`（Electron 注册了这个自定义协议）。Tauri 没有 `coolma` 这个 scheme，只能靠 `convertFileSrc('', 'coolma-resource')` 拿运行时地址，前端把**运行时地址直接写进了正文**：`http://coolma-resource.localhost/<kb>/<doc>/<name>`
- **实测证据**（sql.js 只读探针，两库对照）：
  - Tauri 库 `%LOCALAPPDATA%\cn.coolma.tauri\memocast.db`：184 篇笔记，`coolma://` 形态 2 篇、`.localhost` 形态 2 篇、`index_files` 相对引用 0 篇
  - Electron 库 `%APPDATA%\coolma\memocast.db`：184 篇，`coolma://` 2 篇、`.localhost` 0 篇
  - 结论：两边存的是**同一个内容、不同形态**。"存运行时地址"本身不是 bug（原本也存运行时协议），真正的 bug 是形态不一致导致的单向锁死——迁移过来的 2 篇老笔记在 Tauri 里图片是裂的（`coolma` scheme 未注册），Tauri 新写的笔记回到 Electron 也裂
- **改法**：新增 `src/desktop/noteResources.js` 做双向纯函数转换，DB 层只在 `content` 上挂两刀
  - 写：`db:updateNote` 的 `content = ?`、`db:createNote` 的 UPDATE / INSERT 三处，落库前调 `toCanonicalResources()`，运行形态（`http(s)://coolma-resource.localhost/`、`coolma-resource://localhost/`）一律归一成 `coolma://coolma.app/`
  - 读：`execToObjects()` 出口对 `content` 调 `toRenderableResources(content, resourceUrlBase())`，规范形态换回当前平台运行形态；不含 `coolma` 字段直接短路，base 懒计算一次
  - `wizResources.js` 导出 `resourceUrlBase()`（Tauri 返回 `convertFileSrc` 前缀，非 Tauri 返回规范前缀）
- **不改什么**：`index_files/<name>` 相对引用与站外链接原样保留；`embedMDNote` 上传为知的替换逻辑本就同时认两种形态，无需动；老数据不写迁移脚本，下次保存即自我修正
- **验收**：Jest 新增 `tests/note-resources.test.js`（13 条）覆盖两种运行形态归一、多图、幂等、往返一致、`index_files` 不受影响、空值；`jest` 9 suites 52 tests 全绿，`eslint` 94（`database/index.js` 基线 94，无新增）

### P2-8 拖拽图片入正文无效（P2-3 只解决了一半） —— 状态：已完成（真机反馈发现）

- **现象**：用户实测「直接拖拽不行，得点插入图片再选择文件」。P2-3 加了 `dragDropEnabled: false`，HTML5 `drop` 确实能收到了，但正文还是没反应
- **根因**：Muya 的 `contentState/dragDropCtrl.js:135-175` 用 `file.path` 取本地绝对路径（**Electron 给 `File` 加的私有属性**），再把它交给 `imageAction` 上传。WebView2 是标准 Chromium，`file.path` 恒为 `undefined` → 先写 `![loading-xxx](undefined)`，再 `uploadImage(undefined)` 里 `fetch(undefined)` 抛错 → 被 catch 成"上传失败"，正文什么都不留
- **改法**：新增 `src/desktop/muyaImageDrop.js`，Tauri 环境下在编辑器容器的 **capture 阶段**接管 `dragover` / `drop`（抢在 Muya 自己的冒泡监听前面）
  - `drop` 里取 `dataTransfer.files` 中的 `File` **对象本身**（不需要路径），直接交给 store 的 `uploadImage(file)` —— 与「插入图片 → 选择文件」对话框完全同一条链路，`wizOfficialImageUploadService` / `picgoServer` / `none` 三种服务都已在 actions.js 里支持 `File`
  - 上传拿到 src 后调 Muya 公开 API `contentEditor.insertImage({ alt, src })`，插到当前光标处（与粘贴图片的行为一致）
  - 只筛 `image/*`；非图片文件、拖入链接、以及非 Tauri（浏览器预览）路径全部不接管，原逻辑照旧
- **验收**：Jest 新增 `tests/muya-image-drop.test.js`（10 条）覆盖单图/多图插入、无文件不拦截、非图片不拦截、上传失败回调 onError 且不插坏 src、空 src 不插、dragover 仅图片 preventDefault、capture 解绑；`jest` 10 suites 62 tests 全绿，`eslint` 新增文件 0、`Muya.vue` 42（基线 42，无新增）
- **已知边界**：插入位置是"当前光标"而不是"鼠标落点"（Muya 没有坐标转光标的公开 API）；拖拽表格/单元格内的位置同样按光标走
