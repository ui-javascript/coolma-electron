# TODO — 竞品分析

> 整理日期：2026-07-29
> 收敛日期：2026-11-21
> 范围：以外部竞品视角，评估 coolma / Memocast 的技术复杂度、差异化能力、竞品位置与短板
> 结论先行：**项目有真实差异化（rune / echo DSL + 本地优先同步 + 博客发布管道），但仍处在“个人作品”阶段；优势在可编程 Markdown 与写作发布一体化，短板在文档、社区、移动端和协作**
> 边界：本文只做产品与竞品分析

## 0. 评估标尺

四个维度同时看，避免“这个功能我喜欢”的主观偏差：

1. **技术复杂度** — 看复杂度是壁垒还是负担
2. **差异化** — 竞品是否也做、做得深不深
3. **用户价值** — 解决谁的什么问题，是否可替代
4. **可执行性** — 按当前小团队规模，能否持续维护

### 1.2 复杂度归类

| 维度 | 评分（满分 5） | 评估 |
| --- | --- | --- |
| **架构复杂度** | 4 | Electron 主进程 + 渲染进程 + 3 个独立 Vue 子应用，wujie 微前端 + vuex + SQLite IPC + electron-store 混用 |
| **核心编辑引擎** | 4 | 二次封装 Muya，加 Monaco 双编辑器 + Block 树扩展 + 自研 `@xxx{...}(...)` 注解体系 |
| **数据 / 同步层** | 5 | 本地 SQLite（`sql.js`）+ 为知笔记云端双向同步，覆盖删日志、空笔记补回、kbGuid 映射、跨账号隔离、2004 错误回退 |
| **试验特性（rune / echo）** | 5 | 自研 DSL：16 张内置 echo + 14 个 SFC rune 模板 + 工厂 + jQuery handler 字符串编译 + 完整 Jest 契约测试 |
| **桌面能力** | 3 | 离线 store + 自动更新 + 窗口状态 + 7z 压缩；缺协作与移动端 |
| **测试护城河** | 3 | 11 个 Jest 套件覆盖 rune / echo 关键契约；云函数、DB schema、Muya parser、序列化解码仍有缺口 |
| **UI 库混用** | 3 | Element-UI × Quasar × Ant Design Vue 三栈混用，有规约但维护负担明显 |

> **一句话**：这不是“小项目”。复杂度主要集中在有产品意义的部分——编辑器扩展、同步层、可编程 DSL，而不是无意义堆代码。

### 1.3 复杂度为什么不是纯负担

- 大多数复杂度服务于核心差异化（rune / echo / 同步），不是补丁式堆功能
- 编辑器切换、同步、插件加载三条主线在 `superpowers` 规则体系下有清晰边界
- 关键链路有 Jest 锁定契约，重构风险相对可控

## 2. 差异化能力

### 2.1 强差异化

#### A. Echo 注释体系

> Markdown 行内用 `@echo名{props}(文本)` 触发 DOM 增强。

16 张内置卡片覆盖富表达：高亮、复读、折叠高亮、忽略、todo、广告标注、参考资料、diff 标记、双生花（克隆行）、破万法（屏蔽其他 echo）、天行健（切主题）、离析（松排版）、招灾（哥特渐变）、夺心魄（劫持其他 echo）、替罪（兜底）、强运（AI 校对）。

- **核心差异**：echo 与 echo 之间可以互相作用（破万法屏蔽、夺心魄劫持）
- Obsidian / Notion / Typora 都没有同类“装饰互动 DSL”
- 配合 rune 形成**可编程富文本**：作者在 Markdown 里写一个 `@xxx{...}` 就引入一个交互式组件

| 工具 | 类似能力 | 差距 |
| --- | --- | --- |
| Obsidian | Dataview、Plugin 钩子 | 插件式，要安装并学习专有 API |
| Notion | 块类型 + 子页 / 数据库 | 块类型封闭，作者无法自定义块语义 |
| Typora | 自定义 HTML 标签 | 只能写死样式，不能劫持其他 echo |
| coolma | `@xxx{props}(text)` 行内 DSL | **作者可编排 echo 之间的互动** |

#### B. Rune 远程导入与微前端内嵌

- `runeRemoteImportDialog` 支持从 GitHub URL 直接经 `hel-micro` 拉取 Vue SFC 到笔记里
- 任意前端工程师写一个 rune 模板 → 推到 GitHub → 用户一键导入
- 这是**第三方模板分发的雏形**，价值在扩展模板来源与复用，而不是封闭的内置组件库

#### C. 本地优先同步模型

- `SyncService` 显式声明“不与传统 conflict 合并兼容”
- 备份 / 恢复 / 删日志队列 / 空笔记补回 / 跨账号隔离 / 2004 错误回退策略完整
- 对离线场景友好：断网仍可写，恢复后自动备份

| 工具 | 同步模型 | 差距 / 优势 |
| --- | --- | --- |
| Obsidian | 官方同步服务 + 第三方插件 | 本地方案更可预测，不依赖单一托管 |
| Notion | 实时双向 | 协作强，离线弱 |
| Typora | 无原生同步 | 不具备本地优先队列 |
| 为知笔记 | 双向 + 冲突解决 | coolma 的本地优先语义更明确 |

#### D. 博客发布管道（写作 → 发布）

- `BlogDeployService` + VuePress 1.x
- 一键把本地笔记打包成静态博客（vuepress / vdoing / hope / reco 主题）
- 支持 SFTP 推送 + GitHub Actions
- 中间产物 `id-mappings.json` / `seq-manifest.json` 解决 permalink 冲突
- 是少有的“写作 → 发布”一体化桌面工具

| 工具 | 类似能力 | 差距 |
| --- | --- | --- |
| Obsidian | Digital Garden / Quartz 插件 | 插件式，配置成本高 |
| Memos | 一键公开页 | 仅适合短内容，不能吃完整 Markdown 能力 |
| Notion | 第三方托管服务 | 依赖外部平台，控制力弱 |
| coolma | 原生内置 | **优势：原生 + 全功能 Markdown** |

#### E. 富交互元素嵌入

- markmap 思维导图
- jsxgraph 数学互动画板
- reveal.js / Marp PPT 模式
- 写作时插入一个 `@jsxgraph{...}` 就能在笔记里跑数学交互
- 这是**写作 + 学习工具的合流**，与 Notion 的“嵌入第三方”是不同理念

### 2.2 中等差异化

- 标签 treemap（替代传统标签列表）+ 日历筛选
- AI 长对话 + 思考过程动画 + 流式输出 + 一键应用回笔记 + 多供应商切换
- 皮肤系统（哪吒红 / 12 星座 / MBTI 等主题方向）

这些能力提升体验，但竞品大多能通过插件、主题或 AI 功能补齐，不构成独家壁垒。

### 2.3 偏弱项

- 同步后端绑定为知笔记，用户群与场景受限
- 文档、教程、社区几乎空白
- 没有移动端，交互未针对触摸设计
- 不支持协作，仍是单兵作战产品
- 品牌认知弱，外部几乎搜不到有效内容

### 3.2 竞品位置判断

- 对 **Obsidian**：coolma 的差异在行内 DSL 与原生发布管道，不在通用插件数量。正面拼插件生态没有胜算。
- 对 **Notion / 语雀**：coolma 的差异在本地真存与离线可控，不在协作和云端体验。正面拼协作没有胜算。
- 对 **Typora**：coolma 更重，但多了同步、发布、扩展能力；对纯写作用户反而更复杂。
- 对 **Logseq / Memos**：coolma 功能更完整，但更重、更桌面化；轻量记录场景不占优。
- 对 **为知笔记**：既是同步后端也是竞品；coolma 的编辑扩展与发布能力更强，但用户基础远弱。

## 4. 差异化结论

### 4.1 真正能称为壁垒的部分

1. **echo / rune 的可编程 Markdown 模型**：行内 DSL + 组件模板 + 互相作用机制，竞品没有同类实现
2. **本地优先同步队列**：离线写入、恢复后备份、跨账号隔离等边界处理完整
3. **写作 → 发布一体化**：桌面端直接打包静态博客并推送，不依赖第三方托管

### 4.2 不能当壁垒的部分

- AI 对话与改写：模型能力可替换，竞品都在做
- 皮肤、标签 treemap、日历：UI 层差异，容易被复制
- 多编辑器切换：工程量大，但用户感知有限

### 4.3 当前定位

**“可编程 Markdown 桌面工作台”**，而不是“又一个 Notion 替代品”。

- 适合：愿意写 Markdown、需要本地数据控制、有发布需求、愿意折腾扩展的重度用户
- 不适合：要多人协作、移动端优先、开箱即用的普通用户

## 5. 短板与风险

| 风险 | 严重度 | 现状 | 应对方向 |
| --- | --- | --- | --- |
| **技术栈老化** | 高 | Vue 2.7.16 EOL、Element-UI 维护期、VueI18n 8 停更；技术栈决策已明确不整体升级 | 单库评估替换 + 关键库保留 + 新组件独立 Vue3 栈 |
| **文档缺失** | 高 | README 极简、无架构图、无用户手册、无 API 文档 | 先补 echo / rune 开发文档与最小上手指南 |
| **品牌认知弱** | 高 | GitHub 与搜索结果几乎没有有效曝光 | 用可编程 Markdown 主题做内容输出，而不是泛泛推广 |
| **依赖为知笔记** | 高 | 同步后端只支持为知 | 已在 `TODO-云函数调研存档-202607.md` 评估 uniCloud + vk-router |
| **国际化不完整** | 中 | i18n 已做，但 rune 名词与部分 UI 字符串未翻译 | SDK 化前补英文文档与术语表 |
| **单兵作战** | 中 | 按 1 人节奏维护 | 控制范围，优先守住编辑器、同步、发布三条主线 |
| **协作 / 移动端空白** | 中 | 架构未考虑触摸与多人实时协作 | 不在当前阶段正面投入，避免摊薄核心能力 |

## 6. 当前不建议投入的方向

| 方向 | 不建议理由 |
| --- | --- |
| 通用笔记工具（正面对标 Notion / Obsidian） | 头部太强、用户习惯已固定；本地优先与可编程扩展才是细分空间 |
| 企业协作 / 多人协作 | 权限、SSO、实时协同全部空白，当前规模无法填补 |
| 移动端重写 | 现有架构未考虑触摸，重构成本极高 |
| 自建云端 | 与已选的云函数方案冲突，且运维负担大 |
| 纯 AI 助手作为主叙事 | 模型能力同质化，竞品覆盖充分，难形成独立认知 |

---

## 7. 待确认的竞品假设

- 是否把 **echo / rune 可编程 Markdown** 作为对外第一叙事，而不是“功能很多的笔记软件”
- 是否先补开发者文档与模板示例，再谈扩展生态
- 为知同步是否作为长期底座，还是按云函数方案逐步解耦
- 是否接受“重度用户的小众工具”定位，不追求大众笔记市场
- 是否把博客发布作为核心使用场景之一，而不是附属功能
